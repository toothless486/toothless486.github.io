> 대상: **Onyx(구 Danswer)** · 대응 스택: **BGE-M3 + TEI + Qdrant** · 한국어 회사 문서 RAG

RAG 시스템의 성능 문제는 "모델이 느리다"로 뭉뚱그려지기 쉽지만, 실제로 돈과 시간을 잡아먹는 지점은 모델 바깥에 있는 경우가 많다. 같은 텍스트를 두 번 임베딩하고, 이미 계산한 벡터를 버리고 다시 만들고, 필요 없는 순간에 무거운 추론을 돌리는 식이다.

Onyx(구 Danswer)는 오픈소스 사내 검색·RAG 플랫폼이고, 이 문제들을 실제 PR과 공식 문서에 남겨 두었다. 그래서 "이론상 이렇게 하면 좋다"가 아니라 **프로덕션이 실제로 선택한 것**을 확인할 수 있다.

병목은 크게 두 갈래로 갈린다. 배치로 도는 **색인 경로**와 사용자가 기다리는 **검색 경로**는 없애야 할 것이 서로 다르다.

| 경로 | 장 | 무엇을 없애나 |
| --- | --- | --- |
| 색인 | 1~4장 | 중복 임베딩 · 재작업 · 메모리 폭증 |
| 검색 | 5~8장 | 사용자 대기 구간의 지연 |

색인 경로에서 없앨 낭비는 셋이다. 1~3장이 각각을 다룬다.

- 문서를 다시 색인할 때 **바뀌지 않은 청크까지 전부 다시** 임베딩
- 같은 질문이 반복해서 들어오는데 **매 요청마다 쿼리를 다시** 임베딩
- 대량 색인 중 중단되면 **처음부터 다시** 시작

## 1. 변경 없는 문서 스킵

### 핵심 원리

재색인은 "문서 전체를 다시 넣는" 작업이 아니라 **"바뀐 부분만 반영하는"** 작업이어야 한다. 판단 기준은 **콘텐츠 해시(content hash)**다.

```
청크 텍스트 → 해시(sha256) → 저장된 해시와 비교
                                   │
              ┌── 같음 ──▶ 스킵 (임베딩 안 함)
              └── 다름/없음 ──▶ 임베딩 후 upsert + 새 해시 저장
```

### 무엇을 해시할 것인가 — 두 단계

| 레벨 | 해시 대상 | 목적 |
| --- | --- | --- |
| 문서 레벨 | 원본 파일 전체 (또는 `updated_at`, 등) | **파일이 통째로 안 바뀌었으면** 청킹·해시 계산조차 스킵 |
| 청크 레벨 | 청크 텍스트 문자열 | 파일 일부만 바뀐 경우 **바뀐 청크만** 골라 재임베딩 |

> 문서 레벨 필터를 먼저 통과시키면 대부분의 파일은 청킹 단계 전에 걸러진다(가장 큰 절감). 살아남은 파일만 청크 레벨로 정밀 비교한다.

### 안정적 청크 ID가 핵심

청크마다 **내용과 무관하게 안정적인 ID**가 있어야 "이 청크가 그 청크"임을 추적할 수 있다.

```
chunk_id = f"{doc_id}:{chunk_index}"        # 위치 기반 (단순)
# 또는
chunk_id = sha256(doc_id + normalized_text) # 내용 기반 (재정렬에 강함)
```

- **위치 기반**: 구현 단순. 단, 문서 중간에 문단이 삽입되면 뒤 청크 인덱스가 밀려 전부 "변경"으로 오판될 수 있음
- **내용 기반**: 텍스트가 같으면 위치가 밀려도 동일 ID → 재정렬에 강함. 회사 문서처럼 편집이 잦으면 이쪽 권장

### 삭제 처리

재색인 시 **이번 문서에서 사라진 청크 ID는 DB에서 삭제**해야 유령 데이터가 안 남는다.

```
새 청크 ID 집합 = {A, B, C}
기존 청크 ID 집합 = {A, B, D}     (D는 이번에 삭제됨)
──────────────────────────────
임베딩(신규/변경): A·B·C 중 해시가 바뀐 것만
Qdrant 삭제:      D
```

### 해시/상태 저장 위치

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| Qdrant payload에 `content_hash` 필드로 저장 | 벡터와 한곳에서 관리, 별도 저장소 불필요 | 비교 위해 조회 필요 |
| 별도 KV(SQLite/Redis) | 조회 빠름, 색인 파이프라인과 분리 | 저장소 이중 관리 |

## 2. 쿼리 임베딩 캐시

### 핵심 원리

검색 챗봇은 사용자 질문이 들어올 때마다 **쿼리 → 벡터** 변환을 한다. "영업시간 알려줘" 같은 **반복 질문**을 매번 임베딩하는 건 낭비다. 결과 벡터를 캐시해 두고 재사용한다. **처리량보다 응답 지연(latency)** 관점에서 특히 이득이다.

```
질문 → 캐시 조회
         ├─ Hit  ──▶ 저장된 벡터 반환 (임베딩 스킵, 지연 거의 0)
         └─ Miss ──▶ TEI 임베딩 ──▶ 캐시에 저장 후 반환
```

> **TEI**: Text Embeddings Inference — Hugging Face가 만든 임베딩·리랭커 모델 전용 고성능 추론 서버(Rust 기반)

### 정확 매칭 vs 의미 매칭

| 방식 | 캐시 키 | 특징 | 위험 |
| --- | --- | --- | --- |
| **정확 매칭(Exact)** | 정규화된 질문의 해시 | 구현 단순·안전. 글자 하나만 달라도 Miss | 낮음 |
| **의미 매칭(Semantic)** | 쿼리 벡터 유사도 | "몇 시까지 해?" ≈ "영업시간?"도 Hit | 임계값 느슨하면 **엉뚱한 캐시 반환** |

> **권장 순서**: 먼저 **정확 매칭**부터 도입한다(위험 0, 반복 질문·자동완성·재시도에서 즉시 이득). 의미 매칭은 트래픽이 커지고 유사 질문이 많다는 게 확인된 뒤에, 신중히 얹는다.

### 정규화가 Hit율을 좌우

같은 질문인데 Miss가 나면 캐시 의미가 없다. 키 생성 전 정규화 필수.

```
# 연속 공백·개행 → 단일 공백
# 필요 시: 끝의 물음표/구두점 제거
```

> ⚠️ **BGE-M3 프롬프트 규칙 주의**: 만약 쿼리 측에 instruction 접두어를 붙이는 규칙을 쓴다면, **접두어를 붙인 최종 입력**을 기준으로 캐시해야 색인·검색 규칙과 어긋나지 않는다.

- TTL 설정 (문서/정책 변경 반영 주기 고려)

## 3. 체크포인트 증분

### "체크포인트 증분"이란

- **체크포인트(checkpoint)**: 대량 색인 작업의 **진행 상태를 특정 시점에 저장**해 둔 지점
- **증분(increment)**: 매번 전체를 다시 저장하는 대신, **직전 체크포인트 이후 처리한 만큼만** 이어서 기록

즉 **체크포인트 증분** = 수만~수십만 청크를 색인하는 긴 배치에서, **중간중간 "여기까지 했다"를 이어붙여 기록**해 두는 것. 그래야 중단되어도 **처음부터가 아니라 끊긴 지점부터** 재개할 수 있다.

```
전체 저장:  매 배치마다 [전체 진행 상태 통째로]  ← 느리고 낭비
증분 저장:  [배치1 완료] → [+배치2 완료] → [+배치3 완료]  ← 처리한 만큼만 이어붙임
```

### 왜 필요한가 — 대량 초기 색인의 현실

한국어 회사 문서 전량 초기 색인은 수 시간이 걸릴 수 있다. 이때:

- **중단은 반드시 일어난다**
- 체크포인트가 없으면 중단 = **처음부터 다시** → 이미 임베딩한 수만 청크를 또 GPU에 태움 (가장 큰 회피 대상)

### 무엇을 체크포인트에 기록하나

| 항목 | 예시 | 용도 |
| --- | --- | --- |
| 커서(진행 위치) | 마지막 완료 `doc_id` / 배치 번호 / 파일 오프셋 | 재개 시작점 |
| 완료 집합 | 이미 upsert 끝난 `chunk_id`들 | 중복 upsert 방지 |
| 모델 태그 | `bge-m3@v1` | 모델 바뀌면 체크포인트 폐기 |
| 통계 | 처리·스킵·실패 수 | 모니터링·검증 |

## 4. 인덱싱 파이프라인 스트리밍 배치

> 출처: Onyx(구 Danswer) v3.2.0 — *"Indexing pipeline streams chunks through a unified iterable-based abstraction with batched processing, improving memory usage and throughput on large corpora"*
> 관련 PR: 색인 인터페이스 `list`→`Iterable`, 어댑터 스트리밍화·enricher 패턴, 디스크 기반 배치
> — <https://github.com/onyx-dot-app/onyx/pull/9384> , <https://github.com/onyx-dot-app/onyx/pull/9469> , <https://github.com/onyx-dot-app/onyx/pull/9468>

### 핵심 원리

**"만들어야 하는 임베딩을 어떻게 흘려보내(stream) 메모리를 평탄하게 유지하느냐"**다. 핵심은 **모든 청크를 리스트로 한꺼번에 메모리에 올리지 않고, 한 번에 하나씩(one-pass) 흘려보내며 배치로 처리**하는 것.

하나의 큰 파일이 **수천 개 청크**로 쪼개질 때, 소박한 파이프라인은 각 단계(청킹→임베딩→메타데이터→색인)마다 **청크 전량을 리스트로 materialize**한다.

특히 **임베딩 단계에서 메모리가 급등**한다. 청크 N개 × 벡터(BGE-M3 기준 1024차원 float) 전부를 동시에 들고 있어야 하기 때문.

```
[나쁨] 문서 → 전체 청크 리스트 → 전체 임베딩 리스트 → 전체 메타데이터 리스트 → 색인
        (단계마다 청크 N개 전량이 메모리에 상주 → 큰 문서일수록 메모리 폭증)

[좋음] 문서 → 청크 스트림 ─┬─▶ 배치 임베딩 ─┬─▶ 청크별 메타데이터 부착 ─┬─▶ 색인
        (한 번에 배치 크기만큼만 메모리에 존재 → 문서 크기와 무관하게 메모리 일정)
```

### 메모리 프로파일 — 이 설계가 사는 이유

같은 파이프라인을 **시간축의 메모리 사용량**으로 보면 차이가 분명해진다.

```
[나쁨] 단계마다 materialize
  메모리 ▲
        │      ┌────┐ 전체 임베딩 리스트 (N × 1024 float)
        │  ┌───┘    └───┐
        │  │ 전체 청크    └──┐ 전체 메타데이터
        │──┘                └────────
        └──────────────────────────────▶ 시간
         ⇒ 문서가 커질수록 메모리 폭증 (O(N))

[좋음] 스트리밍 + 배치
  메모리 ▲
        │  ┌┐ ┌┐ ┌┐ ┌┐ ┌┐ ┌┐   배치 크기만큼만 톱니 모양
        │──┴┴─┴┴─┴┴─┴┴─┴┴─┴┴──
        └──────────────────────────────▶ 시간
         ⇒ 문서 크기와 무관하게 일정 (O(batch))
```

- 나쁜 쪽의 봉우리는 **임베딩 단계**에서 가장 높다. 청크 리스트가 아직 살아 있는 상태에서 벡터 리스트가 얹히기 때문.
- 좋은 쪽은 톱니의 **높이가 배치 크기로 고정**된다(Onyx의 `MAX_CHUNKS_PER_DOC_BATCH`가 이 높이를 정한다).

### 체크리스트

- [ ] 배치 크기를 **TEI 배치·GPU VRAM**에 맞춰 튜닝
- [ ] 스트리밍 시 **같은 문서 청크는 연속으로** 흘려보내기(문서 경계 flush)
- [ ] 문서 단위 **all-or-nothing**(실패 시 해당 doc 롤백)으로 반쪽 색인 방지

## 5. 리랭킹 격리 — 지연에 민감한 추론을 색인 부하에서 분리

> 출처: Configure Onyx (model server 분리 배포) · Index Settings
> — <https://docs.onyx.app/deployment/configuration/configuration> , <https://docs.onyx.app/admins/advanced_configs/search_configs>

리랭킹은 두 단계로 나뉜다.

1. 쿼리 벡터와 가까운 문서 벡터 찾기 — "질문이 찍힌 지점에서 거리상 가장 가까운 문서 100개를 가져와라"
2. 이 후보들을 실제로 한 권씩 펼쳐서 질문과 대조해 읽어보고(크로스 어텐션), 진짜 답이 있는 문서의 랭킹을 올림

```
쿼리: "How many people live in Berlin?" (베를린에 몇 명이 사나요?)
요소: ① 사람 수(how many people), ② 거주(live), ③ 베를린(Berlin)

후보 문서 3개:
"Berlin had a population of 3,520,031 registered inhabitants…" → 점수 8.61 (1위)
"In 2013 around 600,000 Berliners were registered in sport and fitness clubs" → 점수 6.35 (2위)
"Berlin has about 135 million day visitors…" → 하위
```

세 문서 모두 "Berlin"과 숫자가 들어 있어서 벡터 유사도로는 비슷해 보인다. 크로스 인코더는 질문의 "how many people live"를 문서와 대조해 읽기 때문에 "거주 인구"를 말하는 1번에 압도적으로 높은 점수를 주고, 숫자는 크지만 "방문객" 얘기인 문서를 아래로 내린다.

### 왜 리랭킹이 격리 대상인가

리랭커(크로스 인코더)는 검색 경로에서 성격이 유독 튀는 부하다.

- **무겁다**: 쿼리+문서를 **한 쌍씩** 모델에 통과시킨다. 후보 50~100개면 GPU 추론 50~100쌍
- **동기적이다**: 응답 직전, **사용자가 기다리는 구간**에서 돈다

이런 부하를 색인 임베딩과 **같은 프로세스·같은 GPU**에 두면 문제가 생긴다.

### 서버 구조

```
                            ┌──────────────┐
                            │   챗봇 UI     │
                            └──────┬───────┘
                                   │
                     ┌─────────────▼──────────────┐
                     │        App (Spring/API)     │
                     └──┬──────────────────────┬───┘
                        │                      │
        ┌───────────────▼──────────┐   ┌───────▼──────────────┐
        │  TEI (query)  :8080      │   │  Indexing Worker     │
        │  ─ 쿼리 임베딩 (BGE-M3)   │   │  ─ 해시 비교/스킵     │
        ├──────────────────────────┤   │  ─ 청크 스트리밍      │
        │  TEI (rerank) :8081      │   │  ─ 체크포인트         │
        │  ─ bge-reranker-v2-m3    │   └───────┬──────────────┘
        │                          │           │
        │      ★ GPU A (질의)       │   ┌───────▼──────────────┐
        └──────────────────────────┘   │  TEI (index)  :8082   │
                                       │  ─ 배치 임베딩         │

   ─────────────────────┴──────────────────────┴─────────────────────
        ┌────────────────────────────────────────────────┐
```

## 6. 리랭킹 의도 분류 모델

> **의도 모델의 정체** — [`hybrid-intent-token-classifier`](https://huggingface.co/Danswer/intent-model)

쿼리 자체가 keyword형으로 분류되면 리랭킹을 스킵한다.

- 의도 분류는 쿼리가 키워드형인지 의미형인지 판별한다.
- 키워드 head는 모든 토큰 각각에 대해 "이 토큰이 핵심 키워드인가"를 분류한다.

```
쿼리 → DistilBERT 인코딩 1회
         ├─ [의도 head]  쿼리 전체가 keyword형? semantic형?   ← 쿼리 단위 판단
         └─ [키워드 head] 각 토큰이 핵심 키워드인가?           ← 토큰 단위 판단
```

두 갈래의 예: "휴가 신청 양식" vs "연차를 내려면 어떤 양식을 작성해야 하나요?"

keyword형으로 분류되면 하이브리드 검색의 가중치(α)를 BM25 쪽으로 기울인다. 다만 키워드 head가 뽑아낸 토큰 자체는 아직 검색에 쓰지 않는다 — "추출된 키워드는 아직 신뢰할 만하지 않아서 당장은 사용하지 않는다. 하이라이팅에는 쓸 수 있을 것"이라는 게 현재 입장이다.

## 7. 전처리 병렬화

> 출처: Onyx PR "improved basic search latency"
> — <https://github.com/onyx-dot-app/onyx/pull/4186>

### 문제 — time-to-first-docs가 높다

에이전트 방식(LLM 기반 문서 필터링)과 리랭킹을 함께 켜면, 툴 선택(tool choice) 이후 **1~2초**의 지연이 붙었다. 의도 분류 → 쿼리 임베딩 → 필터 → 리랭킹이 **순서대로** 돌았기 때문이다. 사용자 입장에서는 필터링·리랭킹이 "문서를 보내기 전에" 다 끝나야 해서 첫 문서가 늦게 도착한다.

### 대기 구간을 유용한 계산으로 채운다

LLM이 **툴 선택을 하는 그 시간 동안**, 어차피 검색이 선택되면 필요할 계산을 **미리·병렬로** 돌려 둔다.

- **의도 모델**: 쿼리를 keyword형 / 비-keyword형으로 분류
- **쿼리 임베딩**: 벡터 검색용 (precomputed query embedding)

```
[전] 의도분류 ──▶ 쿼리임베딩 ──▶ retrieval     (직렬 합산)
[후] 의도분류     ─┐─(병렬)─▶ (검색 확정 시 결과 즉시 사용) ─▶ retrieval
     쿼리임베딩    ┘
```

"검색"으로 확정되는 순간, 임베딩과 의도 분류는 **이미 계산되어 있다** → 검색 단계가 바로 retrieval로 진입한다.

## 8. 검색 자체를 병렬로 — keyword ∥ vector ∥ 청크 조회

> 출처: Starlog 분석 · DeepWiki: Document Search and Indexing Backends
> — <https://starlog.is/articles/llm-engineering/onyx-dot-app-onyx/> , <https://deepwiki.com/onyx-dot-app/onyx/8.5-document-search-and-indexing-backends>

### 하이브리드 검색을 병렬 실행

Onyx의 하이브리드는 **keyword와 vector검색을 직렬이 아니라 병렬로** 던지고 결과를 병합한다. 점수 병합(정규화 vs RRF)

### 청크 조회 병렬화

**청크 조회를 왜 하나**: 검색 인덱스는 응답을 가볍게 유지하려고 청크 ID + 점수만 반환하고 본문은 주지 않는다. 하지만 뒷 단계 — 리랭커(청크 텍스트), LLM(컨텍스트 본문), UI(메타데이터) — 는 모두 본문이 필요하다.

## 부록 A: Onyx의 인덱스 설계 — 무엇을 어떤 값으로 인덱싱하나

> 출처: `danswer_chunk.sd.jinja`(Vespa 스키마) · `confluence/connector.py` · `indexing/chunker.py`
> — <https://github.com/onyx-dot-app/onyx/blob/main/backend/onyx/document_index/vespa/app_config/schemas/danswer_chunk.sd.jinja>

1~8장이 "어떻게 빠르게"였다면, 이 부록은 **"애초에 무엇을 인덱싱하는가"**의 참조 자료다. Onyx의 인덱스 설계는 소스 코드의 Vespa 스키마 파일 하나에 전부 선언되어 있다.

### 용어 정리: 임베딩 ⊂ 인덱싱

임베딩은 인덱싱 전체 파이프라인 안의 **한 단계**다.

```
① 가져오기   커넥터가 원본(페이지 본문·댓글 등) 수집
② 청킹       텍스트를 검색 단위로 분할
③ 임베딩     각 청크를 벡터로 변환            ← 여기가 임베딩
④ 저장       검색엔진에 두 종류의 색인 구축
             ├─ 키워드 인덱스 (원문 텍스트 → BM25 역색인)
             └─ 벡터 인덱스   (임베딩 결과 → HNSW)
```

- ④의 키워드 인덱스는 임베딩과 무관한 전통적 역색인이다 — **임베딩 없는 인덱싱도 있다**.
- 임베딩만 하면 벡터가 생길 뿐 검색이 안 된다 — **인덱싱 없는 임베딩은 검색이 아니다**.
- 원문 텍스트 자체도 통째로 저장된다. 벡터는 "관련 청크 찾기"까지만 하고, LLM 프롬프트에 넣을 본문은 저장된 원문에서 가져와야 하기 때문(벡터에서 원문 복원 불가).

### 청크 1개 = 인덱스 문서 1개 — 필드별 인덱스 종류

Onyx는 청크마다 Vespa 문서 하나를 만들고, 필드별로 서로 다른 인덱스를 건다.

| 인덱스 종류 | 필드 | 용도 |
| --- | --- | --- |
| **키워드(BM25 역색인)** | `title`, `content` **딱 2개** | 키워드 검색은 제목·본문에서만 |
| **벡터(HNSW, angular=코사인)** | `embeddings`(청크 본문, multipass 시 미니청크 포함), `title_embedding`(제목 별도) | 의미 검색 |
| **필터/조회(attribute, fast-search)** | `document_id`, `tenant_id`, `chunk_id`, `access_control_list`(권한), `document_sets`, `metadata_list`, `personas`, `hidden`, `boost`, 날짜 | RDBMS 인덱스와 가장 유사 — 필터·랭킹 재료 |

- BM25 역색인: 자료구조(역색인)와 점수 계산식(BM25)이 한 세트로 동작하는 검색
- 키워드 검색 = 역색인(자료구조) + BM25(랭킹)
- 벡터 검색 = HNSW 인덱스(자료구조) + 코사인 유사도 등(랭킹)
- RDBMS = B-Tree 인덱스 + 트리 탐색(tree traversal)

### 인덱스 대상 필드는 알고리즘이 아니라 사람이 고른다

BM25·HNSW는 **"어떻게 쌓고 점수 매기나"**를 담당할 뿐, **"어떤 필드에 걸지"**는 스키마 설계자의 선택이다. RDBMS와 정확히 같은 구조:

| | 사람이 정하는 것 (필드) | 알고리즘이 하는 것 |
| --- | --- | --- |
| RDBMS | `email` 컬럼 | B-tree가 정렬·탐색 |
| 키워드 검색 | `title`, `content`에 `enable-bm25` 선언 | BM25가 토큰화·역색인·점수 계산 |
| 벡터 검색 | `embeddings`, `title_embedding`에 HNSW 선언 | HNSW가 그래프 구축·근사 최근접 탐색 |

- 필드를 고른 **다음부터는** 자동이다: 키워드 인덱스는 토크나이저가 본문을 단어 단위로 알아서 쪼개 색인하고("어떤 단어를 넣을지"는 사람이 안 고름), 벡터 인덱스는 들어오는 벡터로 그래프를 알아서 쌓는다.
- 사람은 알고리즘 **파라미터**(BM25의 k1/b, HNSW의 M/ef, 거리 함수)까지는 조정하지만, 필드 선택을 알고리즘이 대신하지 않는다.

**Onyx 개발팀의 실제 선택** — BM25는 `title`·`content` 2개뿐(작성자·URL·메타데이터엔 안 걸음), HNSW는 `embeddings`·`title_embedding` 2개(거리 함수 angular=코사인). 눈에 띄는 포인트는 **제목을 양쪽에 이중 반영**한 것이다:

```
제목 ──┬─▶ title           (BM25 키워드 축)
       └─▶ title_embedding (HNSW 벡터 축)
본문 ──┬─▶ content         (BM25 키워드 축)
       └─▶ embeddings      (HNSW 벡터 축)
```

키워드든 벡터든 **"제목 vs 본문" 두 축을 일관되게 유지**했기 때문에, 검색 시 하이브리드 점수도 제목 점수와 본문 점수를 비율(`title_content_ratio`)로 섞는 대칭 구조가 된다(아래 rank profile 참고).

### 임베딩 입력 텍스트의 합성 규칙 (chunker)

Document가 그대로 임베딩되는 게 아니라, chunker가 청크마다 임베딩 입력을 이렇게 합성한다.

```
[문서 제목 (title prefix)]          ← 모든 청크 앞에 붙음
[청크 본문 텍스트]
Metadata:
    {key} - {value}                 ← 자연어 문자열로 뒤에 붙음
```

```
원본 문서 (예: Confluence 페이지 1개)
   │  ① 텍스트 추출
   │  ② 청킹 (Onyx 기준 약 512 토큰 단위)
   ▼
청크 1 ─→ Vespa 문서 1  { content, 임베딩 벡터, title, 메타데이터 }
청크 2 ─→ Vespa 문서 2  { content, 임베딩 벡터, title, 메타데이터 }
청크 3 ─→ Vespa 문서 3  { ... }
```

### 실례: Confluence 커넥터는 어떤 값을 넣나

| Confluence 값 | Document 필드 | 메타데이터 인덱스 (attribute) | 키워드 인덱스 (BM25) | 벡터 인덱스 (임베딩) | 비고 |
|---|---|:---:|:---:|:---:|---|
| 페이지 제목 | `title` | − | ✅ | ✅ | title prefix로 임베딩에 포함 + `title` BM25 인덱스 |
| 페이지 본문 (HTML→텍스트 변환) | `sections` | − | ✅ | ✅ | 청크로 분할되어 임베딩의 메인 콘텐츠 + `content` BM25 인덱스 |
| 페이지 댓글 | `sections` | − | ✅ | ✅ | `"Comment:"` 프리픽스 붙여 별도 섹션으로 본문과 함께 색인 |
| space 이름, labels | `metadata` | ✅ | − | ✅ | `Metadata: space - XX` 문자열로 임베딩에 포함 + `metadata_list` 필터 인덱스 |
| 페이지 URL | `id` | ✅ | − | − | 문서 ID·결과 링크 (임베딩 제외, 저장만) |
| 작성자 이름·이메일 | `primary_owners` | ✅ | − | − | 임베딩 제외, 저장만 |
| 생성일·수정일 | `doc_created_at` / `doc_updated_at` | ✅ | − | − | 임베딩 제외 — recency 부스트·시간 필터용 |
| 첨부파일 | 별도 `Document` 생성 | − | − | − | 페이지에 합쳐지지 않고 별도 문서로 분리 인덱싱 (`parent_hierarchy_raw_node_id`로 상위 페이지 연결) |

### 검색 시 세 인덱스가 함께 쓰이는 순서

위 세 종류의 인덱스는 질의 한 번에 다음 순서로 조합된다.

1. **메타데이터 필터로 범위를 먼저 좁히고** (예: 해당 호텔 + 한국어 문서만) — 필터/조회 인덱스(attribute) 사용. 권한(`access_control_list`) 필터도 이 단계에서 걸린다.
2. 그 안에서 **키워드 검색(BM25)과 벡터 검색을 동시에 실행**한 뒤 — 역색인과 HNSW가 각각 후보를 뽑는다 (병렬 실행의 지연 이득은 8장 참고)
3. 두 결과를 **RRF(Reciprocal Rank Fusion)나 리랭커(reranker)로 합쳐** 최종 순위를 만든다 — Onyx의 Vespa는 rank profile의 가중 수식으로, 우리 스택은 RRF 병합(+선택적 리랭킹, 5장)으로 처리

```
질의 → [① 필터: 호텔=X, lang=ko, 권한]         ← attribute 인덱스
        └→ [② BM25 ∥ 벡터 검색]  (동시 실행)   ← 역색인 ∥ HNSW
              └→ [③ RRF / 리랭커 병합] → 최종 순위
```

> ①을 먼저 거는 이유: 후보 모수 자체가 줄어 ②의 검색 비용·노이즈가 같이 줄고, 권한 필터를 검색 이후 앱에서 거르는 방식(후필터)보다 top-k가 필터로 깎여 모자라지는 문제가 없다.
